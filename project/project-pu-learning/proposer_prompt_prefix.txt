You are working on a Positive-Unlabeled active-search science task. Your goal is to implement a better selection policy that discovers as many known positive candidates as possible under a limited query budget.

## High-Level Goal
There is a fixed candidate pool, usually 5000 rows from a larger CSV. A separate positive CSV defines known positives. All other candidates are unlabeled/unknown, not clean negatives.

In each round, your policy selects 100 NEW candidates. An oracle reveals whether each selected row is in the hidden positive set. The evaluation score is based on the positives discovered in the current evaluation run.

## What You Are Allowed To Change
Do NOT modify anything except the model implementation file.
Do NOT change function signatures or IO behavior.
Do NOT read the positive CSV, generated label files, or hidden evaluator internals.

## Policy Interface
Your model code must provide one of:
1) A module-level function:
   select(candidates, history, batch_size, seed) -> list[int]
2) A class with a select(...) method named SelectionPolicy, Policy, or Model.

## Input Semantics
candidates:
- A list of row dicts for the full search space.
- Does NOT include hidden labels.
- Does NOT include the positive CSV path.

history:
- A list of previously queried row dicts.
- Each row includes original fields plus:
  - candidate_index: int
  - label: int, 1 means matched the known positive set, 0 means not found in that set.

Important PU constraint:
- label=0 is an unlabeled miss/noisy negative. It is not proof that the candidate is truly bad.
- You may use label=0 as weak evidence, but do not build a strategy that assumes all unlabeled examples are clean negatives.

## Constraints
- Return candidate indices only.
- Avoid repeats and already-selected indices.
- Be robust when history is empty or has no positives yet.
- Run fast on about 5000 candidates.

## Useful Strategy Ideas
- Extract numeric features from candidate rows.
- Cold start with diverse exploration.
- Once positives appear, exploit regions similar to positives.
- Use unlabeled misses as low-weight noisy negatives.
- Mix exploitation, uncertainty/exploration, diversity, and small random perturbations.
- Re-rank top candidates for diversity so each batch does not collapse into one tiny region.

If available, inspect the previous run's harness/outputs/metrics.json. Its queried_history contains only rows that were actually queried and oracle-labeled.
